How it works

Three steps. No dashboard required.

Everything is an API call. If your agent can make HTTP requests, it can have a mailbox in under a second.

1

Create an inbox

POST /v1/inboxes returns a stable delivery URL plus a read secret and a write secret. Secrets are shown once — store them.

2

Point webhooks at the URL

Stripe, GitHub, cron jobs, or another agent — anything that can POST can deliver. Sources that can't set headers just append ?write_secret=….

3

Your agent reads the mail

GET /v1/inboxes/{id}/messages lists new arrivals, newest first. Process each one, then DELETE it to acknowledge.

Quickstart

From zero to receiving in 30 seconds.

Run the server locally, create an inbox, deliver a message, read it back. Base URL below is http://localhost:8000.

1 — create an inbox 
# Create an inbox. Save url, read_secret and write_secret — shown once.
curl -s -X POST http://localhost:8000/v1/inboxes \
  -H "Content-Type: application/json" \
  -d '{"label": "deploy-watcher"}'

# → 201 {"id":"mbx_8fK2…","url":"…","read_secret":"…","write_secret":"…","created_at":"…"}
2 — deliver a message 
# Deliver with the write secret. Any content type, up to 256 KB.
curl -s -X POST http://localhost:8000/v1/inboxes/INBOX_ID \
  -H "X-Write-Secret: WRITE_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"event": "payment.succeeded", "amount": 4200}'

# → 202 {"message_id":"msg_…","received_at":"…","signature_valid":null}

Webhook sources that can't set headers (Stripe, GitHub): append ?write_secret=WRITE_SECRET to the inbox URL instead of sending the header.

3 — read the mail 
# List messages, newest first. Then DELETE each one to acknowledge it.
curl -s "http://localhost:8000/v1/inboxes/INBOX_ID/messages?limit=10" \
  -H "X-Read-Secret: READ_SECRET"

curl -s -X DELETE http://localhost:8000/v1/inboxes/INBOX_ID/messages/MSG_ID \
  -H "X-Read-Secret: READ_SECRET"
API reference

Small enough to memorize.

Eight endpoints. JSON everywhere. Auth is a single header per call — no OAuth dance, no SDK required.

MethodEndpointAuthWhat it does
POST /v1/inboxes — Create an inbox. Body: {"label": "optional"}. Returns 201 with id, url, read_secret, write_secret, created_at.
POST /v1/inboxes/{id} X-Write-Secret
or ?write_secret=		 Deliver a message. Any content type, 256 KB cap. Optional X-Signature-256 header for HMAC-SHA256 verification. Returns 202 with message_id, received_at, signature_valid.
GET /v1/inboxes/{id}/messages X-Read-Secret List messages, newest first. ?limit (default 50), ?before_id for keyset pagination. Each message carries id, received_at, content_type, body, headers, signature_valid.
DELETE /v1/inboxes/{id}/messages/{message_id} X-Read-Secret Acknowledge a message — deletes it after your agent has processed it.
GET /v1/inboxes/{id} X-Read-Secret Inbox info, including message_count.
POST /v1/inboxes/{id}/rotate X-Read-Secret Rotate both secrets. The old pair stops working immediately; the new pair is returned once.
DELETE /v1/inboxes/{id} X-Read-Secret Delete the inbox and every message in it. Irreversible.
GET /health — Liveness probe. Returns {"status":"ok"}.
For agents

Usable unassisted.

The repo ships a SKILL.md. Drop it into your agent's skills folder and any agent — Claude Code, Cursor, and friends — can provision inboxes, hand the delivery URL to webhook sources, and drain mail on a schedule, with no human in the loop.

The intended loop is simple: a scheduled worker polls /messages, handles each arrival, and DELETEs it. The inbox is the decoupling point between the event and whatever runtime wakes your agent.

This page documents the contract; the skill teaches the workflow. Together they're the whole integration.

agent polling loop — python 
import requests, time

API = "http://localhost:8000"

# once: provision a mailbox, point webhooks at inbox["url"]
inbox = requests.post(f"{API}/v1/inboxes", json={"label": "deploy-watcher"}).json()
iid, rsec = inbox["id"], inbox["read_secret"]
hdr = {"X-Read-Secret": rsec}

# forever: drain new mail
while True:
    msgs = requests.get(f"{API}/v1/inboxes/{iid}/messages",
                        headers=hdr, params={"limit": 20}).json()
    for m in msgs["messages"]:
        handle(m)  # your logic here
        requests.delete(f"{API}/v1/inboxes/{iid}/messages/{m['id']}", headers=hdr)
    time.sleep(60)
Security model

Built like infrastructure, not a demo.

A public POST endpoint is a promise. Here's how that promise is kept.

Unguessable inbox IDs

IDs are cryptographically random. There is no enumeration — you can't find an inbox you weren't given.

Secrets shown once, stored as hashes

Read and write secrets are returned a single time at creation or rotation, then stored only as salted hashes.

Read/write separation

The delivery key can't read mail; the read key can't deliver. A leaked webhook URL never exposes message contents.

HMAC webhook verification

Send X-Signature-256 with deliveries; the server verifies the HMAC-SHA256 and reports signature_valid on every message.

Rate limiting

Per-inbox and global limits on deliveries and reads. One noisy sender can't crowd out the rest.

7-day retention, then purged

Messages live for seven days and are then deleted automatically. Acknowledge with DELETE to clear them sooner.

Sensitive headers redacted

Authorization-style headers on incoming deliveries are stripped before storage — they're never persisted or returned.

256 KB message cap

Oversized deliveries are rejected before they're stored. The inbox stays a mailbox, not a file host.
